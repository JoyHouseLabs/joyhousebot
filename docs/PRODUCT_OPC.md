# Joyhouse OPC 产品定位与引擎边界

状态：Accepted（2026-08-09）
适用范围：Joyhouse、JoyhouseBot、Task Pack、官网与产品控制台

## 1. 一句话战略

> OPC 是目标用户，长期持续任务是产品机制，成果与收入增长是用户价值，JoyhouseBot 是底层执行引擎。

Joyhouse 面向一人公司，也服务希望持续成长、积累个人能力和作品的个人。它不出售“万能 Agent”，而是
让研究、经营、创作和复盘等重要循环在用户不在线时继续推进。

## 2. 品牌结构

| 品牌 | 面向对象 | 责任 | 不承担 |
| --- | --- | --- | --- |
| Joyhouse | 普通用户、独立开发者、一人创业者 | 个人智能系统；目标、经营状态、确认、成果与连接管理 | 暴露 Run、Graph、Capability 等引擎概念 |
| JoyhouseBot | 开发者、自部署用户、扩展作者 | 开源、可本地部署的长期任务执行引擎 | 重建 CRM、ERP、项目管理或内容平台 |
| Smart Study | 有成长与学习需求的用户 | 基于相同理念形成的独立垂直产品 | 作为 JoyhouseBot 默认插件或 Core 参考业务 |
| Task Pack | Joyhouse 用户和创作者 | 可安装、购买、分享和派生的持续任务产品 | 绕过 Runtime 权限、审批、版本和 Eval |

普通用户主要接触 Joyhouse；JoyhouseBot 作为可信执行基础设施存在。只有自部署、开发扩展或排查运行问题
时，用户才需要进入 JoyhouseBot Console。

## 3. 核心承诺

产品承诺：

> 连接你的目标、数据和工具，让重复经营工作持续运行，并把每次执行沉淀为真正属于你的业务资产。

面向用户的表达：

> 即使你不在线，公司里的重要事情也在按照你的目标持续推进。

“持续推进”必须由真实机制支撑：定时或事件唤醒、持久 Run/Task、上下文积累、人工确认、失败恢复、结果
投递、证据与成果版本，而不是一个常驻聊天窗口或无法审计的无限 Agent loop。

## 4. OPC 的核心问题

一人公司的稀缺资源是持续注意力：

- 市场、竞品和用户需求无法每天跟踪；
- 想法、资料、客户信息与决策分散；
- 内容选题、创作、发布和反馈无法形成循环；
- 线索没有及时补充背景、跟进和复盘；
- 项目交付依赖个人记忆，阻塞出现得太晚；
- 每周完成很多零散工作，却没有形成可复用资产。

一次性问答和一次性代码生成有价值，但不会天然维护这些经营循环。Joyhouse 的产品对象因此是“有目标、
有状态、有节奏、有确认点、有成果”的持续任务。

## 5. 第一批持续任务产品

### 5.1 市场与机会雷达（第一切口）

持续跟踪竞品、用户需求、技术变化和市场信号，形成带来源和证据的每周决策简报；用户确认后把结论写入
关注对象、观点和下一步实验。

### 5.2 内容经营

根据用户资料、已确认观点与业务方向维护选题池，生成草稿，等待确认后发布，并把渠道反馈带回下一轮。

### 5.3 客户线索跟进

汇总表单、邮件和私信中的线索，补充背景，提示下一动作，持续追踪未回复客户；高风险外发必须确认。

### 5.4 项目推进

根据目标、里程碑和交付日期检查进展，识别阻塞，提醒下一动作，定期生成面向客户的进度报告。

### 5.5 经营与个人成长复盘

每周汇总完成事项、收入线索、内容表现、项目进度、重要决策和能力积累，形成下一周经营计划。个人成长
不是独立的聊天功能，而是执行证据、决策、技能、作品和复盘随时间形成的长期资产。

## 6. Task Pack 产品契约

Task Pack 是面向用户的可安装持续任务单元，不等同于 Python 插件。一个版本化 Task Pack 可以引用：

- 目标说明、适用对象和可衡量结果；
- Workflow / Scenario / Agent revision；
- Schedule 或 Event Trigger 模板；
- 所需 Channel、Connector、Tool、Knowledge Provider；
- 最小权限、数据分级、成本上限和人工确认点；
- 初始化问题和用户事实 Schema；
- 输出 Artifact / Work 类型、证据要求和投递方式；
- Eval dataset、质量阈值、升级与回滚规则；
- 面向 Joyhouse 的状态卡片和结果展示元数据。

安装 Task Pack 只创建草稿和依赖检查，不自动授予权限、不自动连接外部账号、不自动开始付费调用。用户
完成连接、审阅节奏/成本/确认点并显式启用后，Runtime 才创建 Automation/Schedule 并进入统一 Run 链路。

Task Pack 的定义和版本属于可分享资产；用户的目标、客户、邮件、上下文和执行结果保持私有，不能随
Task Pack 分享。

## 7. 产品与引擎结构

```text
用户已有工具
邮件 / 日历 / GitHub / 文档 / 表单 / 内容平台
                    │ extension contracts
                    ▼
                 Joyhouse
目标 / 个人事实 / 持续任务 / 待确认 / 经营状态 / 成果
                    │ versioned HTTP + SSE
                    ▼
               JoyhouseBot
Run / Task / Schedule / Approval / Recovery / Audit / Artifact / Work
                    │
                    ▼
                PostgreSQL
```

Joyhouse 保存轻量但关键的个人事实源：身份与业务、当前目标和项目、产品与关注对象、客户关系索引、已
确认观点和决策、运行中的持续任务，以及已形成的内容、报告和作品。外部系统仍保存其擅长的完整业务数据。

JoyhouseBot 不增加某个 Task Pack 的业务表、专属页面或硬编码流程；业务能力通过独立扩展注册。

## 8. Joyhouse 首页

首页围绕经营状态，而不是空聊天框：

- 今天需要你确认；
- 正在持续运行；
- 本周发现的新机会；
- 等待跟进的客户；
- 即将交付的项目；
- 本周形成的成果。

聊天用于创建和调整任务，例如“持续关注 AI 视频工具市场，每周五形成机会简报”。系统生成目标、来源、
频率、预算、确认点和输出结构供用户审阅；启用后，用户主要处理确认、查看结果和调整目标。

## 9. 商业边界

Joyhouse 面向 OPC，不采用企业席位作为主要计费单位。可按活跃持续任务、频率、连接器和资源用量分层：

- 基础版：少量低频持续任务；
- 专业版：更多任务、更高频率和更多连接器；
- 专业 Task Pack：市场研究、内容经营、线索跟进等；
- 模型、搜索和外部服务超额用量；
- Task Pack 创作者市场分成；
- JoyhouseBot 自部署免费，官方云托管收费。

## 10. 当前优先级与非目标

第一产品切口是独立开发者和一人创业者的“市场机会与经营研究台”。它优先使用 Email、网页研究、文档和
定时任务，不要求先建设完整 CRM。

当前非目标：

- 建设完整 ERP、CRM、财务、邮件客户端或项目管理系统；
- 同时接入所有聊天渠道；
- 用“万能 Agent”替代清晰的持续任务产品；
- 为企业租户模型引入 `tenant_id`；
- 把 Smart Study 重新并入 JoyhouseBot。

## 11. 产品衡量

优先衡量结果而非聊天量：

- 持续任务启用后 4 周留存；
- 每周按计划完成且证据充分的任务比例；
- 用户处理确认所需时间；
- 从发现到用户决策/行动的转化；
- 形成并复用的 Work、观点、Skill 和 Task Pack 数量；
- 每个有效成果的成本、失败恢复率和人工返工率；
- 可归因的线索、交付、内容或收入增长。
